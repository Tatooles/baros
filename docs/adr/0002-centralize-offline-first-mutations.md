# Centralize offline-first mutations

Every owner-scoped, user-originated syncable mutation must run through one internal transaction module. Each transaction explicitly declares its owner, which must match the Current Owner before changes begin; cloud authorization is not required for local access. Domain modules explicitly name each create, update, or delete action because they own the rules that determine the correct action; the transaction module does not infer those rules. Each named action wraps the corresponding model change and records its outbox intent, preventing the change and intent from drifting apart. One transaction may contain several named actions, but it saves once, requests sync once, and rolls back every action if any part fails. A transaction with no named actions returns successfully without saving or requesting sync. Before starting, the module requires that the SwiftData context contain no unsaved domain-model changes, while allowing normal unsaved `SyncOutboxEntry` bookkeeping created by an in-progress sync. If unrelated domain changes are present, the module rolls back to the last successful save and returns a recoverable error; user input remains in a separate draft so the user can retry. The module requests sync only after a successful save.

Domain modules retain their exercise, settings, and workout rules. Active Workouts remain local and outside this transaction path until they become Logged Workouts. This trades caller flexibility for one enforceable offline-first guarantee and one test surface as the app grows.

Unclaimed Local Data records ownerless outbox intents, the same as owner-scoped data. It has no owner destination yet, so those intents cannot be pushed until an owner claims them; they are kept because they carry two things nothing else does. They are the durable record that the user changed a row locally, which sync preparation reads to claim rows after the one-time bootstrap and seed merging reads to tell a signed-out edit of a re-seeded duplicate apart from a fresh default — without them such an edit is deleted uncopied. And they are the route to the cloud for data created while signed out, which would otherwise depend entirely on a bootstrap pass that runs once per owner. An earlier revision of this decision left the unclaimed path outbox-free and replaced that signal with per-run adoption passes; each consumer of the signal it did not replace surfaced as a separate data-loss bug, so the intents are kept and the adoption passes remain only as a migration safety net for stores written before them. Those passes still matter for records that legitimately carry no intent: a Logged Workout finished while signed out on an older build, or an upgraded store whose rows predate this tracking. Sync preparation therefore runs re-runnable adoption over ownerless Logged Workouts and over ownerless settings and exercise records, both guarded by the policy that blocks adoption when another owner's data is present on the device. The exercise pass excludes seeded rows, because signed-out mode re-seeds the default library as ownerless rows and adopting them would duplicate the owner's own seeds. It adopts the settings singleton only when the owner has no row of its own: owned and ownerless settings coexist as separate rows, so adopting unconditionally would either leave the account with two owned singletons or overwrite its preferences with local mode's. Where bootstrap deliberately declines to merge pre-existing Unclaimed Local Data into an account that already had remote workout history, it records the declined sessions by identifier so they stay local while later ones remain eligible. Identifiers are recorded rather than a cutoff timestamp because no field records when a session became a Logged Workout: `createdAt` is stamped when the Active Workout starts, so a workout drafted before a decline and finished after it would be excluded forever, and `endedAt` is rewritten by duration edits. A cursor row that predates this tracking carries no declined list, and an empty list must not be read as consent to upload; such a row is evaluated once on its next sync, which declines every Logged Workout that is unclaimed at that moment except a graph with an active legacy ownerless outbox intent. That intent is durable evidence that the graph was already intended for upload, so sync preparation adopts the complete graph from its current model state and reconciles existing intents, newly added children, and tombstones before upload. Owner-scoped changes always create outbox entries even when cloud synchronization is paused or the device is offline.

Unclaimed Local Data does not get a second transaction module: it runs through the same one, via a separate entry point that drops the Current Owner comparison — unclaimed data stays editable no matter who is signed in, so deleting local history from another account must not be rejected — and declares a `nil` owner, which makes every target's ownership check require an ownerless row and every recorded intent ownerless. Save, rollback, outbox recording, and scheduling are otherwise identical, so the two paths cannot drift apart.

As a narrow safety guard, the transaction module rejects a workout, logged exercise, or logged set that is not part of a Logged Workout. It does not own workout completion rules or status transitions; those remain in the workout domain module.

The `SyncOutboxTransaction` module exposes one throwing `perform` seam that returns `Void`. Returning normally means the owner-scoped transaction succeeded or had no actions; it does not mean cloud synchronization completed. Its transaction value is available only inside that operation and provides explicit `create`, `update`, and `delete` actions that wrap domain changes. SwiftData saving, rollback, outbox recording, ownership validation, and post-save sync remain hidden behind the seam. `SyncScheduler` is a required dependency, and every successful non-empty transaction requests sync exactly once after saving; the scheduler decides whether synchronization can run immediately. A paused scheduler keeps the durable outbox work queued while the Current Owner remains able to edit local data. Tests exercise the same interface with the existing in-memory SwiftData container rather than introducing an adapter protocol.

The interface uses a closed target list named by domain role: `userSettings`, `exerciseLibraryEntry`, `loggedWorkout`, `loggedExercise`, and `loggedSet`. The module owns the exhaustive mapping from those targets to the existing SwiftData model types, outbox entity kinds, identifiers, ownership, and sync eligibility. This keeps outbox knowledge out of the persisted models and makes support for each new synced model an explicit change in one place.

The app creates one `SyncOutboxTransaction` with its main `ModelContext` and `SyncScheduler`, then injects it into the domain modules that perform synced mutations. It is app-scoped rather than a global singleton. Tests construct independent instances with an in-memory context and test scheduler.

The transaction interface is the primary test surface for persistence and outbox guarantees. Its tests cover every target and action, ownership, multi-action rollback, unexpected domain-change recovery, allowed in-progress outbox bookkeeping, no-op behavior, scheduling, and active-draft rejection. They also verify that changing a target while its outbox entry is in flight returns the entry to pending so the newer state remains queued. Domain-module tests continue to cover exercise, settings, and workout rules without duplicating the transaction sequence.

All existing user-facing syncable mutation paths migrate to this module before the change merges. Implementation proceeds in stages—transaction module and contract tests, settings and exercise-library mutations, logged-workout completion and history mutations, then removal of duplicated save, rollback, outbox, and scheduling code—without leaving competing transaction patterns in the merged codebase.

The seam covers user-originated domain changes only. Applying downloaded changes, maintaining or retrying the outbox, seeding and bootstrap, and account-deletion recovery remain outside the module because they manage replication itself and must not enqueue their own work for upload.

The transaction module never claims Unclaimed Local Data automatically. An ownership or domain workflow may explicitly assign it to the Current Owner when existing rules allow; the transaction validates that each target's final owner matches the declared owner before saving. Data that remains unclaimed or belongs to another owner causes the operation to roll back.

When an operation fails, the module rolls back and rethrows the original domain or persistence error. It introduces its own errors only for transaction rules such as unexpected unsaved domain changes or ownership mismatch, preserving the real cause for logs and tests while allowing the UI to present a simpler message.

Whichever layer performs the save owns the matching rollback, no other layer may roll back on top of it, and every rollback preserves the unsaved outbox bookkeeping already in the context — a sync suspended at its network `await` has marked an entry in flight without saving it, and reverting that would push an already-completed mutation again. The transaction module owns both the owner-scoped and unclaimed paths, and the Active Workout engine owns its own draft saves. Callers therefore present the error without rolling back: a second `rollback()` after a failed transaction would discard the unsaved in-flight outbox bookkeeping the module just restored, resurrecting an already-completed intent or returning an in-flight entry to a status that pushes it twice. The same rule keeps a suppressed Active Workout save failure from leaving dirty models behind, which the transaction preflight would otherwise read as unrelated state and discard when the workout is finished; the user's keystrokes stay in the view-local draft so the failure is retryable, and the view surfaces the real save error rather than the preflight's recoverable one.
